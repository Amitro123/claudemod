# Collector performance, 2026-11

`evidence.py` spent its time starting `git` processes (about 0.1 to 0.4 s each on this Windows machine,
and the machine's speed drifted by 5x between runs). The work was cutting the number of calls and
overlapping the rest, with the normalized results held identical.

Measure with `--timing` (or `INSPECTOR_TIMING=1`): wall time and git calls per phase, on stderr, never in
`evidence.json`. Compare two runs with `python plugins/inspector/tests/normalize.py A/evidence.json B/evidence.json --out-a A --out-b B`.

## Inputs

- (a) skills repo, `--ref origin/main` (e86fa2c) `--path mods/model-router --max 25 --history 80`: 8 units, 4 fixes, 5 copies left behind.
- (b) synthetic repo (`tests/synth.py build_big`, 52 PRs), `--max 200 --history 200`.
- (c) this repo, `--ref 92974e4 --max 30 --history 40`: 30 units, 15 fixes, 11 fix-of-fix, 17 copies, 29 units with version bumps (the richest check).

|---|---|---|

| (a), same session, adjacent | 159.5 s, 769 calls (wall 2m40) | 7.4 to 8.4 s on a quiet machine; 30 to 37 s under load |

| (c) this repo | 235.8 s, 1669 calls | 12.7 s, 412 calls |

Run-to-run noise was large (identical (a) runs: 7.4, 8.1, 8.4, 30.3, 37.1 s), so the table gives ranges. Even the worst
"after" run is 4x faster than the best "before" run. Per phase for (a), same-session before vs a quiet after:

| phase | before | after |
|---|---|---|
| discovery | 10.2 s, 103 calls | 1.3 s, 76 calls |
| changes (stats, version bumps) | 10.8 s, 133 calls | 1.3 s (7 s under load), 2 to 12 calls |
| blame (diff + blame) | 35.6 s, 380 calls | 3.7 s, 77 calls |
| copies left behind | 102.0 s, 134 calls | 0.2 to 1.0 s, 1 call |
| output (dossiers) | 0.9 s, 17 calls | 0.5 to 1.9 s, 17 calls |

Targets: the 25-unit window at least 3x faster or under 60 s: met (about 20x on a quiet machine, 4x to 5x worst case
under load, always under 60 s). Identical normalized results: met (below).

## What changed

1. Unit stats: one `git log --first-parent --numstat -M` instead of a `git diff --numstat` per unit; version bumps
   from one `git log -p -U0 --no-renames` over the manifest names only instead of one `git diff` per manifest per unit
   (133 calls to 2). Long windows are cut into `--skip/--max-count` slices that run side by side.
2. Discovery: the work window is a bare `git log --format=%H`, not a second full walk with a `git log` per merge;
   `rev-parse` facts (shallow, toplevel, git dir) in one call; the per-merge `git log` calls run on the pool.
3. Fix commits: one `git diff -U0 -M --patch-with-raw` per commit serves both blame and the copies search (it was
   `rev-parse`, `diff --name-status`, a `diff` per file and again in the copies search). One `git blame` per file with every hunk as an `-L`
   range, falling back to one per hunk if git refuses the set.
4. Copies left behind: one `git grep -F -f patterns` for every candidate line of the run (it was one `git grep` per line,
   0.8 s each on the skills repo); hits are matched back to lines in Python, in git's order.
5. Blame cache: `<git dir>/inspector/cache`, keyed by (parent commit, file, ranges, ignore-revs content). `--cache-dir` moves it,
   `--no-cache` turns it off. It is the only thing the collector writes inside `.git`; tests use temp folders.
   The key also holds `BLAME_CACHE_VERSION` in `evidence.py`; bump it whenever what blame stores or how it is computed changes.
6. Threads: `--workers N` (default `min(8, cpu count)`); outputs are assembled in the original order.
7. Excludes: `DEFAULT_EXCLUDES` (`node_modules vendor third_party dist build .venv`) are left out of blame diffs and the copies search.
   `--path` inside one, `--component-root NAME`, or `--no-default-excludes` bring it back; `--exclude PATH` adds more.
   The units' own file lists and stats still include them.

Gains by step, measured by ablation on (a) (a quiet machine; the steps were built together, so these are
differences between settings, not separate commits): batching alone (`--workers 1 --no-cache`) 11.9 to 12.5 s; plus threads 7.4 to 8.4 s; plus a warm cache 3.9 s.

## Did any change alter a result?

No. Normalized `evidence.json` equal to the pre-change collector on (a) (twice), (b) and (c); `evidence.md` and every case dossier equal
apart from the script's own path in the "or run" commands (4 dossiers on (a), 12 on (c)). The golden snapshot
(`tests/golden/small_evidence.json`, made before the changes) holds on four scopes (default, `--path`, `--unit`, `--max`), with
`--workers 1`, `--workers 8`, a cold and a warm cache.

Not done on purpose: no `plugins/**` exclusion and no `--no-renames` on the stats pass. Both would change results
(file lists, line totals, culprits in this repo's generated `plugins/` trees), and rename detection was not the dominant cost
(`git log -M --numstat` over 80 commits of the skills repo: about 7 s with `-M`, 5 to 10 s without). None of the default
excludes occur in the measured windows, so they changed no result there; on a repo where blame lines or copies live under `vendor/`
or `dist/` they would, which is the point.

## Tests

| file | before (recon) | after |
|---|---|---|
| test_evidence.py | 371 s | 69 to 83 s |
| test_golden_history.py | 485 s | 29 to 38 s |
| test_collector_equality.py (new) | n/a | 57 to 72 s (builds the synthetic repo; 7 tests) |

`test_evidence.py` builds its repo once per module and shares collector runs between tests that ask the same question (`inv()`).
`test_golden_history.py` was already module-scoped; its run is now the fast collector, with the blame cache in a temp folder, and it carries
the `slow` marker (`-m "not slow"` skips it). `test_default_out_is_a_new_folder` now compares with forward slashes.
No assertion was removed or weakened.

## Test lanes

- Fast lane (seconds, no repository is built): `python -m pytest plugins/inspector/tests -m "not slow" -q`
- Full slow lane (every slow file in its own pytest process, up to min(4, cpus) at once, one summary table, non-zero exit on any failure): `python plugins/inspector/tests/run_slow.py`
- One file: `python -m pytest plugins/inspector/tests/test_evidence.py -m slow -q`

Slow tests are dominated by git subprocess calls made by the collector under test (about 70-90 percent of the calls per file), not by building the synthetic repositories, so the lever is running files side by side, not a faster builder. Every test uses its own `tmp_path`; the files are safe to run in parallel.
