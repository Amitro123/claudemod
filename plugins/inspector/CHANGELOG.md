# Inspector changelog

## Unreleased

- Added (from a live review of 0.8.1 on Windows, 2026-11-18): `evidence.py --recon`, for looking at a seam before changing it. With `--path` it writes the dossiers of the units that touch the path (5 by default, `--budget` overrides) and stops: no RUN PLAN (saved or inline), no case file, no agents, and a closing `RECON:` line that says so. `SKILL.md` has a `recon <path>` row in its scope table, and `when_to_use` now reaches "about to change a multi-component or high-churn seam"; before, it read "not for fixing one known bug" and an agent asked to edit infra, schema and pipeline together never started it. The reviewer reports that in that run the dossiers of three units kept a column insert, a retention setting and a deploy order from being broken (not re-checked here).
- Fixed: the commands the collector and the plan print for an agent to run began with `python3`, which on Windows is often the Microsoft Store stub. They now begin with `python` on Windows and `python3` elsewhere. `INSPECTOR_PYTHON` names another interpreter (`py -3`, a full path) and wins; a value with spaces is split, not quoted, and a value with shell syntax (`;` `&` `|` `<` `>` `$`, a backtick, parentheses, a line break) or unbalanced quotes is ignored, because the name is written into commands an agent runs. The argument quoting is unchanged: `'#12'` stays in single quotes, which Git Bash and PowerShell accept.
- Changed: `SKILL.md` names `scripts/premerge.py` (it was only in the README, so an agent reading the skill never saw it), says to run the collector in the background on Windows as well as on large repositories, and says to write `python` for `python3` there. To stay inside its 3,900-word budget two rarely used lines (comparing plugin copies, `INSPECTOR_ALLOW_PLUGIN_CHANGE`) moved to `references/run-folder.md`, and a few sentences were shortened.
- Not changed, with reasons: pushing `--path` into the unit discovery (a scoped run on this repository makes 335 git calls, 55 of them in discovery, so it would save at most a sixth and it would change which units blame can attribute to); a thread pool for the git calls (`--workers` already runs blame, copies and dossiers on one, 8 by default; the 65 s measured was on 0.8.1, before the batched reads of 0.8.2); the `.in_use/<pid>` markers (nothing in this repository writes them: they come from Claude Code's own plugin cache); a helper that refreshes a `.agents/skills/inspect` junction (specific to one Cursor setup; the plugin resolves its own folder, and a wildcard in the path is enough).

- Fixed: two leads at the same line were never compared when one `where` was an absolute path and the other relative. In a live run on Windows (2026-11-16) one defect was listed two and three times: a sweeper wrote `C:/Users/.../clone/.claude/skills/x/../../settings.json:6`, a reader `.claude/settings.json:6`. `merge_cards.py` now compares files in one spelling (forward slashes, `.` and `..` resolved, the repository's root from `evidence.json` taken off an absolute path inside it, its letters in any case), for exact duplicates, possible duplicates and `--dedupe-model` alike. A lead's own `where` is not rewritten, and a path outside the repository is still its own file.
- Added: `merge_verdicts.py` refuses to merge (exit 2, nothing written) while the run's plan names a verdict file that is missing or was not passed, and names it. In the same live run the merge ran before the last verifier had finished and wrote a `merged.json` with 7 leads `unverified` and no stop. `--partial` merges what exists on purpose. Leads with no plan beside them merge as before.
- Changed: the verifier is told the values a corrected label may take, in its agent file and in each verifier prompt: `category` is `security`, `broken-flow`, `hardening`, `cost` or `other` (a docs drift or a test gap is `other`), `reach` is `default-on`, `conditional`, `opt-in` or `unknown`. Verifiers had written `docs`, `test-gap`, `doc-drift`, `hygiene` and `correctness`; the normalization of 0.8.2 turned those into `other` after the fact, with a warning each.

- Fixed (review of 4ad47bd): resuming a run skipped the docs-checker and handed out the verifier that waits for it. The docs-checker was planned with no output, so `plan.py --status` could not see its work was unfinished, and it ignored the verifier's `after`. `docs-answers.json` is now the docs-checker's tracked output. While it is missing, empty, not valid JSON or holds no answer (an array with at least one object that has `where` and `text`; `[]` is not an answer), status names the docs-checker to start and lists the dependent verifier as `blocked, do not start yet`; the held verifier still counts as work left, so the exit code stays 1. With valid answers the verifier is handed out and the docs-checker is not restarted. `--status` still writes nothing. Compatibility: a 0.8.2 plan (an `after` on the verifier, a docs-checker with no outputs) gets the same behaviour; an older plan with no `after` is reported as before; a run with no documentation question is unchanged. The file must be strict JSON for status and the release gate (`merge_verdicts.py --docs` still tolerates text around the array). On a host with no WebFetch the plan now says to save one `not stated` entry per question, not `[]`.

- Fixed (review of 4ad47bd): a request the service refused and the run then recovered from by splitting still reported a complete cost. A 413 on a two-unit request, then both units answered with a cost, gave `cost` = the two successes' subtotal and `cost_complete: true` for three attempts. Any failed attempt now leaves the total unknown (`cost: null`, `cost_complete: false`) and the measured subtotal stays in `known_cost`; later successful requests do not make it complete again. Answers, `attempts`, `skipped` and the 40-extra-request cap are unchanged. This is accounting only: nothing shows the refused request was charged.

- Fixed: with no run folder the next command can read, the collector now prints the RUN PLAN itself: which agent to start, by type, with its whole prompt (each case with the command that prints its dossier), then the verify step. It applies when no folder can be written ("nothing saved") and when the folder is the temporary fallback, which a sandbox with a private `/tmp` per command hides from the next command; there the pointer comes first with one `ls` to tell the two apart. Before, such a run got "nothing saved" or a pointer to a file it could not read. Measured on `backtest-01` in the eval sandbox (2026-11-16, 3 runs): in 2 the main conversation worked the cases itself, started no agent and skipped verification, and the case file looked complete; each run found 2 of the 8 key bugs, against 3.0 to 4.3 recorded when an agent in a clean context reads.

- Fixed: `crosscheck.py` died with `UnicodeEncodeError` on a Windows console in cp1255 when a card held a check mark (a live run, 2026-11-16; the workaround was `PYTHONIOENCODING=utf-8`). Only `evidence.py` set its streams to UTF-8. `crosscheck.py`, `handoff.py`, `lint_leads.py`, `merge_cards.py`, `merge_verdicts.py`, `plan.py`, `premerge.py` and `doctor.py` now do too: they print text agents wrote and lines of the repository. `tests/test_legacy_codepage.py` runs five of them as processes with `PYTHONIOENCODING=cp1255` and text cp1255 cannot encode. `evals/gate/check_run.py` and `evals/scorecard.py` are not changed.

- Changed: the docs-checker's answers reach the verifier, not only the handoff. `plan.py --phase verify` puts the leads that carry a documentation question last, so they share the last chunk; the docs-checker is the first agent of the phase, and the plan marks that chunk's verifier "start it only after docs-answers.json is saved". Its prompt names the file: where the documentation settles a lead's doubt the verifier gives the verdict it supports and cites the source, and `not stated` leaves the doubt. The number of chunks does not change, and a run without a documentation question is planned exactly as before. In both live runs the docs-checker ran beside the verifiers, so a lead the documentation had settled was still handed off UNVERIFIABLE (the Stop hook's `additionalContext`, twice; `!` negation in deny rules).
- Changed: a lead whose `where` has no line number but names a file (`path/file.py:_write_atomic`, or the file alone) is logged as a possible duplicate of every other lead in that file (`same file, no line number`), so `--dedupe-model` is asked about it. Such a `where` was never compared: in the second live run one defect was verified twice, as `register_pair.py:_write_atomic` and as `register_pair.py:77`, in two chunks. It is still never merged as an exact duplicate, and a `where` that names no single file is still never compared.

- Changed: `--dedupe-cut` defaults to 0.75 (it was 0.9). A second live run (184 units, 35 leads, 4 logged pairs) left a real duplicate at 0.79 to be verified twice, as the first run had at 0.84. On the 14 pairs of both runs, labelled by hand, the 9 that were one defect scored 0.79 to 0.95 and the 5 that were not 0.03 to 0.16: 0.75 merges all nine and none wrongly. Still 14 pairs from two repositories.
- Changed: one or two leads left over after chunks of 8 are spread over the first chunks (9 each) instead of getting a verifier of their own. Both live runs had 33 leads, chunks of 8, 8, 8, 8 and 1, and the verifier for the single lead cost 85k and 80k tokens. 33 leads are now 9, 8, 8, 8; 10 leads stay 8 and 2. The verifier's description says "at most 9".

- Added: `merge_cards.py --dedupe-model [MODEL]` merges the same defect reported twice before it is verified twice. One request asks a decision model whether each logged possible-duplicate pair is the same defect; a pair at or over `--dedupe-cut` (0.9) is merged exactly as an exact duplicate is (the stronger lead kept, the other's `where` in `merged_from`, its words in `merged_variants`, the probability in `merged_by` and in the log), and never across a pair the model called different. Opt-in: the pairs' `where`, `what` and `impact` go to OpenRouter, so the plan adds the flag only when the collector itself ran with `--decision-model`. A failed request merges nothing and says so. Measured on a live run (12 cases, 33 leads, 10 logged pairs, labelled by hand: 6 the same defect, 4 not): the six scored 0.84 to 0.95 and the four 0.03 to 0.16, the same within 0.03 on three requests ($0.0002 each); at 0.9 five were merged, none wrongly, 33 leads became 29 and five verifier chunks became four. One live run is a small sample.
- Changed: `category` and `reach` outside the values `references/labels.md` allows are normalized by `merge_cards.py` (and a verifier's corrected labels by `merge_verdicts.py`): an unknown category becomes `other`, an unknown reach `unknown` with its text moved to `reach_when`; what was written stays in `category_as_written` / `reach_as_written`, and each change is logged. In the same live run 4 of 33 leads carried an invented category (`consistency`, `correctness`, `hygiene`, `test-gap`) and 4 a sentence as `reach`, and the verifiers invented two more categories.
- Changed: the docs-checker's answers reach the handoff. It replies with a JSON array, the main conversation saves the reply as `docs-answers.json`, and `merge_verdicts.py --docs` (in the plan's command) puts each answer on its lead as `docs_answers`; `handoff.py` prints it beside the doubt (`docs: yes: ... (url)`). It changes no verdict. In the live run the documentation settled a lead that was reported twice, and both copies still read UNVERIFIABLE in `open-bugs.md` because passing the answer on was a step done by hand.

- Changed: the collector starts fewer `git` processes, with the same results. A cold first run on this repository (50 units, 19 fixes, 12 cases, `--no-cache --no-github`) went from 538 calls to 332. The fix commits' diffs come from one `git log -p --no-walk` per 12 commits (it was one `git diff` per commit: 77 to 7). In a big fix's dossier, the culprit subjects come from one `git log --no-walk` per section (it was one `git log -1` per culprit: 70 to 17), the per-file culprits reuse what the blame phase of the same run already found (54 `git blame` calls to 0; a saved run read later with `--show` still asks git), and a unit's fix commits are printed by one `git log -p` (43 `git show` to 12). Each batched read falls back to the per-commit call if git refuses the set. `evidence.json`, `evidence.md` and every dossier are equal to the previous collector's on four inputs (`docs/perf-2026-11.md`). `tests/test_batched_git.py` holds a git-call budget on a synthetic history: a count, because seconds differ by 100x between machines and the number of processes does not.

- Added: a new summary section, `Design changes: terms a unit removed that other files still use` (`design_changes` in `evidence.json`; `design_changes_omitted` when more than 15). In a real run, PR #81 of another repo moved a skill from a 4-tier table to 3 levels while `templates/global.CLAUDE.md` kept saying "4-tier" and "Tier 4". "Copies left behind" only reads lines deleted by fix units and #81 is a refactor, so nothing reported it. For every unit that is not a fix, the collector now takes the words, hyphenated terms (`4-tier`) and number phrases (`Tier 4`) its diff removed from instruction and doc files (SKILL, CLAUDE, AGENTS, GEMINI, README, md under skills/agents/commands/prompts/rules, templates; a deleted file is not counted), keeps those removed at least twice or containing a digit or hyphen, drops stop words, and reports the ones that no file the unit changed still has and that other tracked files still use (changelog, history, decision, tuning-log files and tests do not count as users). A word or hyphenated word without a digit or underscore must also have left 2 or more files and be used in at most 4 files, one of them a doc: on real data the plain words were mostly language, not design. Entries are ranked by removed count, then fewest files using, capped at 15, each with the unit, the term, up to 3 `file:line` (files in folders the unit did not touch first) and a `why`. The existing section and keys are unchanged; the new key and section appear only when there is an entry.
- Added: when a promoted unit's probability is within 0.05 of the cut, the decision-model meta has `near_cut` and the summary says so. The model is not deterministic: two runs moved one unit from 0.50 to 0.48 and another from 0.50 to 0.53. `why` strings and tags are unchanged.
- Changed: `SKILL.md` recommends a short `since <sha>` run right after a batch of fix PRs merges, and describes the new section.

## 0.8.2 (2026-11-15)

- Fixed (review of #137, R137-01): the split budget was spent once per split, and each split sent two requests, so a fully refused 41-unit request made 81 calls against a documented 40 extra. `MAX_EXTRA` is now paid before each extra request is sent and shared across chunks. When it runs out, the error says how many units were not asked, and the answers so far are kept. `meta["attempts"]` counts every request sent, and `requests` stays the count that came back answered. Both go into `evidence.json`.
- Fixed: a request-wide 400 or 422 (a model id the service doesn't know, a changed alpha API) was split down to every unit. 10 units cost 19 requests and read as 10 per-unit refusals with no error. Only 403 and 413 are split now. When no unit of a request is answered and the ones asked alone were refused, the run reports a request-wide error, not per-unit refusals.
- Fixed (open since the 2026-11-14 recheck): a lost reply after a paid one left `cost_complete` true. Any error now leaves the total unknown (`cost: null`), and `known_cost` keeps the subtotal.
- Changed: an email-like string needs a domain that ends in letters, so a pinned version such as `react@18.3.1` stays in a title.
- Changed: the case-reader schema shows `needs_host_check` as a JSON boolean again, with the docs question in its own `docs_question` field. The string example `"false | true | the question"` led readers to write the text `"false"` (11 of 31 leads in one run), which #137 now tolerates.
- Fixed: one email-like string voided the whole decision-model run. On 2026-11-15 OpenRouter's content filter answered `403 Request blocked by content filter: [EMAIL]` to a request of 89 units because two commit subjects carried `Co-Authored-By: X <a@b.c>`; 0 of 89 were answered and the run went on with the regex alone. A one-unit probe showed the same text with `<[address]>` was answered by both `typesafe/jev-1.13` and `google/gemini-decision-1`. `decide.py` now (a) replaces email-like strings with `[address]` in every request body (`decide.scrub`, in `_post`, so `premerge.py` is covered too; it walks the body, not the JSON text, so an escape is never broken), and (b) when the service still refuses a request with a 400, 403, 413 or 422, splits it in halves down to the unit at fault, skips that unit (`meta["skipped"]`, named in a collector warning) and keeps the other answers, at most 40 extra requests per run. A 401, a 429, a 5xx or a network error still stops the run: splitting cannot help.
- Fixed: a pasted command in `OPENROUTER_API_KEY` read as a wrong key. The variable held 74 characters with spaces (the text of a shell command), and the service answered `401 Missing Authentication header`, which sent the diagnosis the wrong way for an hour. A key with whitespace inside is not a key: `decide.ask` sends nothing and says so, without printing the value; a trailing newline is trimmed.

- Fixed: `needs_host_check` written as the text `"false"` counted as set. In a live run (2026-11-15) 11 of 31 leads carried the string, and it is truthy and not in the `true`/`yes` skip list: `plan.py` sent the docs-checker 15 questions of which 11 read just `false` (it answered 4), and `handoff.py` and `lint_leads.py` printed `[needs-host-check]` on those 11 leads and treated their change as unverified. A string that spells false (`false`, `no`, `none`, `null`, `0`, empty) is now no flag, in one shared helper (`leadsio.flag_set`) used by `handoff.py` and `lint_leads.py`, and the same list in `plan.py`, which stays standalone.

## 0.8.1 (2026-11-15)

- Changed: release 0.8.1: version bump so installed plugins pick up the fixes merged in #135.

- Changed: the plan's merge commands now run with `--repair-escapes`, and `merge_verdicts.py` has the flag too. The repair (in `leadsio.py`, shared) doubles a stray backslash only when the file fails with an invalid-escape error and the repaired text parses. It keeps the original as `.orig` and logs each repair. In the same Windows run, a verifier also wrote `C:\Users` raw. `merge_verdicts.py` stopped (`Invalid \escape`), `handoff.py` then found no `merged.json`, and the main conversation spent a turn repairing the file by hand. The prompt rule above asks for forward slashes, and this repair catches what the rule misses: enforced in the tool, not only the prompt.
- Fixed: agents on Windows wrote paths into their JSON files with raw backslashes. In the same keshet-claude-skills run, a sweeper wrote `C:\Users\...`, and `\U` is not a JSON escape, so the file did not load. The sweeper then spent two calls patching it by string replacement. Every prompt that writes JSON (readers, sweepers, verifiers) now asks for paths with forward slashes, which Windows accepts, and for any other backslash to be doubled.
- Changed: `SKILL.md` covers two collisions from a live run of 0.8.0 on keshet-claude-skills on 2026-11-15:
  - A router's per-prompt work budget denied the collector in the main conversation, and a worker ran it instead and summarized its output. When a hook's work budget denies a script step, the step is now repeated in the main conversation.
  - With `OPENROUTER_API_KEY` set, the collector now runs with `--decision-model`. Without the key, it never asks for one.
- Fixed: `plan.py --claim` printed "taken" (exit 3) and "still holds" (exit 4) on stderr, so a host that shows a nonzero exit as Failed showed "No output captured" beside it. The same run showed a reader with 6 of 13 calls "Failed", all of them ordinary claims. The reason now prints on stdout every time.
## 0.8.0 (2026-11-15)

- Fixed (2026-11-14 recheck): `premerge.py` called an incomplete reply a clean check. `decide.parse` leaves out missing, refused and invalid answers, but the report said "0 of 4 questions answered yes. Nothing to look at" even when nothing had been answered.
  - The report now gives answered/total and names each question with no answer as INCOMPLETE.
  - It keeps any valid yes, and states "nothing to look at" only when all four were answered no.
  - An empty diff is SKIPPED without a call.
- Fixed (O114-01): `decide.ask` reported an unknown cost as $0. `cost` is now the total only when every request reported one; otherwise it is `null`, with `known_cost` and `cost_complete`. A reported 0 stays 0, and `evidence.json`'s `decision_model` carries all three.
- Fixed (O114-02): `scorecard_gate.py` passed NaN or infinity (`1e999` in JSON), because no comparison with them is true. A metric or threshold that is not a finite number now fails the gate, and so does precision or recall outside [0, 1]. A real 0 still passes.
- Added: `premerge.py`, an opt-in pre-merge check. It asks a decision model four closed questions about a branch's diff and prints the ones answered yes, with what to look at. It is advisory, fails open and always exits 0. Each question is a kind of wrong assumption behind past culprits (`culprit.assumed` in the cards). On 107 changes of two repositories, the four ranked the known culprits at 0.92 to 1.00. Together they flagged 26 of the 107, including 6 of 7 known culprit cases, for $0.04 in all. Questions about awaits and pattern-based guards flagged half of all changes and were dropped (`evals/premerge/README.md`). The README no longer calls evidence.py offline when `--decision-model` is on.
- Fixed (outside review of 2026-11-14, R114-01..03): the shared queue's resume and claim lifecycle.
  - **R114-01:** `--status` handed the same unfinished card to a reader in every wave of a queue with more than four readers, and a wave of one reader restarted it the per-agent way. Recovery owners are now assigned once across all waves, and a one-reader wave follows the queue's rules.
  - **R114-02:** a claim on a case a re-plan dropped (`--drop`) kept blocking its reader. Claims count only for cases the active plan still has, and the dropped card and claim stay on disk.
  - **R114-03:** the claim path called `{}`, another case's card, or a list "finished", while `--status` did not. Both now use one definition, `card_state`, so only a finished card for the held case releases the hold.
- Fixed: the case-reader schema still showed `"needs_host_check": false`, so a reader kept the flag a boolean and wrote its docs question beside it as `docs_question`. After the change to send only written questions, the 2026-11-14 rerun of UltimateDocResearcher planned no docs-checker and lost three Kaggle questions. `plan.py` now takes `docs_question` when the flag is set, and the schema shows the flag as `false | true | the question`.
- Fixed (second 2026-11-14 inspection of this repository): a reader's claim could still take two cases. The hold check and the stub create were two steps, so claims one reader sent at the same moment could both pass (2 of 3 in 1 of 30 tries), and the hold was read from the stub's `reader` key, which the reader rewrites as it works. The check and the create now run under one lock (`claims/.lock`, a `mkdir`, taken over after 30 s), and each claim is recorded in `claims/<n>`, which only `plan.py` writes.
- Fixed: `merge_verdicts.py` ended in a traceback (exit 1) on a verdict entry that isn't an object or has a non-object `corrected` or `probe_check`; it now refuses the file with every problem named (exit 2). A cards folder with no `*.json` read as zero items and the scripts exited 0 with nothing checked; it is now refused. A BOM on stdin is accepted, as in files.
- Changed: only a `needs_host_check` written as a question goes to the docs-checker. A bare `true` means only the repository or the deployed host can settle it, and is left to the verifier. In two runs on 2026-11-14 every question built from a lead's `what` came back "not answerable from documentation". `case-reader.md` and `labels.md` say to write the question, naming the tool, when public docs could settle it.
- Fixed: docs-checker questions were cut at 300 characters, often mid-sentence (UltimateDocResearcher run, 2026-11-14), so the checker got a question it couldn't answer. A question is now kept whole up to 1200 characters, and a longer one ends with `[cut]`.
- Fixed: `evals/gate/timeline.py` gave a later wave negative durations when one of its agents finished before the first free slot the files show (a queue reader that claims nothing writes no card). Such a wave is now timed from the start of the wave before, with a note.
- Fixed: a case reader could claim every case of the queue at once. In the first live run with the queue (2026-11-14, 10 cases, 4 readers), one reader got case 4, and another claimed the other 9 in one shell loop (`for n in ...; do plan.py --claim $n; done`). The other two readers found every case taken and stopped within 15 seconds, so one reader worked 9 cases one after another and the reader phase took 5m19s. `--claim N` now requires `--reader K` (exit 2 without it) and refuses (exit 4) while reader K still holds an unfinished stub, so the same loop takes one case. Each reader's prompt names its number and says one claim per command, never in a loop. The stub records `reader`.
- Changed: `handoff.py` sorts by the verifier's verdict before the level: seen in production, then REAL before REAL-LOW, then `category: broken-flow` before the rest, then level and reach. On 58 verified leads from two runs, `broken-flow` found 6 of the 10 REAL at precision 0.55. A decision model asked "REAL or REAL-LOW?" did worse (`docs/2026-11-14-severity-by-decision-model.md`), so the order uses the labels the leads already carry.
- Changed: case readers share one queue instead of fixed groups. `plan.py` lists every case for every reader, the cases that touch the most files first. A reader claims its next case with `plan.py --claim <n>`, which writes the stub card only if no file is there (`O_EXCL`), so exactly one reader gets each case and a reader that finishes early takes more. `--status` hands a stub or a broken card file to a restarted reader by name ("first finish cards/<n>.json"), since a claim can't get past it, and lets missing cards be claimed. `timeline.py` shows the queue's readers as one row. Measured 2026-11-14 on 36 cases of three runs: no size measure (lines, files, dossier size) split cases statically better than the noise (the same case was 16% apart between runs, up to 66%), while a shared queue, largest first, cut the simulated reader phase by 7% (605 s to 561 s; ideal 520 s). This replaces the balancing by changed lines, which measured as noise.
- Changed: `case-reader`, `sweeper` and `verifier` are told to send independent reads, searches and `git show`s together in one message. The 2026-11-13 transcripts show 96% of the readers' and sweepers' time going to model turns and 4% to tools, with nearly every turn holding a single call (reader-1: 40 calls in 39 turns, about 5.8 s per turn).
- Changed: a later wave no longer waits for the whole wave before it. At most 4 agents still run at once, but each agent of a later wave starts as soon as an agent before it has written its files, in the order `plan.md` lists them. The sweepers are listed longest first (OUTSIDE-IN, code, docs). On the 2026-11-13 run of this repository, the three sweepers waited 1m29s for the slowest reader with three slots free; replayed with the same agent times, the investigate phase ends at 5m02s instead of 6m31s. `evals/gate/timeline.py` starts a later wave when the first agent of the wave before finished.
- Fixed: a unit the decision model promoted (`--decision-model`) had every non-housekeeping commit marked a fix, so a feature PR with one fix commit inside sent its whole feature commit to blame (#73 in the 2026-11-14 inspection). When some commits' own subjects say fix, only those are the fixes; only when none does is every non-housekeeping commit one.
- Added: `evidence.py --decision-model [MODEL]` (opt-in; default `typesafe/jev-1.13`, cut `--decision-cut 0.5`). One request through OpenRouter's Decisions API asks about every worked code unit the regex calls no fix; a unit at or over the cut becomes a fix (`why`: `decision model: p=… (inferred)`, tag `model-fix`) and is blamed like any fix. A regex fix is never asked or undone. Every asked unit records `model_p`; `evidence.json` records `decision_model` (model, cut, asked, answered, promoted, seconds, cost). A failed call warns and leaves the regex verdicts. Measured on this repository's history after #72 (`evals/decision-fix`): the regex found 17 of 20 fixes, the model all 20, with two false positives. Live on #73-#123: 24 units asked, 0.6 s, under $0.001.
- Changed: a leaner plan. Up to 6 cases the plan starts one `inspector:investigator` (it was 1 or 2); from 7, a `case-reader` takes up to 3 cases, one card each, and `plan.py --per-case` keeps one reader per case (from 3 cases). A phase starts at most 4 agents at once: a larger one is planned as waves of the same phase name (`wave`/`waves` in `expect.json`), and the merge comes after the last wave. Every dispatch entry now lists its own `outputs`. `--per-case` carries into `--phase verify`, like `--drop`.
